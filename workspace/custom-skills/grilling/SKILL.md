# grilling：把用户拷问到共识为止

> 来源：Matt Pocock《Skills For Real Engineers》里的 grilling（MIT 开源，仓库 mattpocock/skills）。这是 grill-me、grill-with-docs 背后共用的访谈方法。原文按 Claude Code 写，这里按 Muse 的用法改写。

## 目标

对一个计划、决定或想法 relentless 地访谈用户，直到达成共识。把访谈对象画成一棵**设计树**：每个决定都会分叉出依赖它的其他决定。

## 一轮一轮问

- **前沿（frontier）**：所有前置条件已经确定的决定，也就是现在就能问、不需要先猜答案的问题。每一轮把整个前沿一次问完：每个问题编号，并给出你的推荐答案，然后等用户回答了再进入下一轮。
- 每一轮的格式：

```
❓ **Q1** - **<问题标题>**：<问题正文，可以多段、可以给选项>

➡️ <你的推荐答案>

---

❓ **Q2** - **<问题标题>**：<问题正文，可以多段、可以给选项>

➡️ <你的推荐答案>
```

- 措辞要让「yes」就等于接受你的推荐答案。

## 每轮之后

- 用户每回答一轮，设计树就变了：已确定的决定会把前沿往外推，解开依赖它们的问题。重新算前沿，再问下一轮。
- 一个问题的答案还依赖本轮里另一个没回答的问题，那它属于**下一轮**，不是本轮。

## 查事实是你的活，不是用户的

- 前沿里某个问题需要一个事实（文件系统、工具、账号状态等），派一个子代理（subagent.spawn）用全新的上下文去查；不要问用户任何你自己能查到的东西。
- 不要等它：正在跑的查证只是一个未确定的前置条件，只有依赖它的下游问题才等它汇报；前沿里其他问题现在就问。

## 决定是用户的

- 每个决定都要摆给用户，等他拍板。

## 什么时候算完

- 前沿为空时结束：设计树的每条分支都走过，没有任何东西被默许。
- 用户确认达成共识之前，绝不要按访谈内容动手。
