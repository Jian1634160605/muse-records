# 成品音频审计报告（2026-10-23）

**审计问题**：最近发布的 FB 成品里，哪些条目的音频混有/留有源片原声（用户反馈"一个视频里面会有两个音乐"）。
**方法**：声学核验，不看脚本下结论。每条成品与参考音轨分别解码为 8kHz 单声道，计算 0.25 秒窗 RMS 能量包络，做 ±8% 时间伸缩 + 小时移搜索的 Pearson 相关（r_music 对指定音乐轨、r_src 对源片原声）；对疑似混合者再做偏相关（剔除音乐成分后源原声的独立相关）；对包络不可分的同曲音轨用 8 频带对数能量频谱指纹复核。全部 18 个成品文件经 ffprobe 核验**均只有 1 条音轨流**，因此"双音乐"只可能来自单轨混音或发布端叠加。
**参考同一性已验证**：音乐池各 .m4a 与对应源视频自带音轨的包络相关均为 r=1.000（池轨确系源片原声的忠实抽取）；Det6A4nIazf / Detu-DrI-Om / DetvfGEIb11 / DevV3l0oYL- 四个池文件 MD5 完全一致（916 Deep Sculpt 系列共用同一条原音轨，下文记作 T）。

## 重点点名

1. **2026-10-20 三条（根目录 _wm 版与 queue/2026-10-20 版是同一批文件）根本没换轨**：整条音频就是源片原声（r=0.999，频谱同实例 0.996–0.997），我方音乐为零。更关键的是发布记录（queue/2026-10-20/posted.txt）：其中 **r2 的 FB 版在发布时用 FB 网页端加了平台热门曲（Adam Griffith · Knockout）**——文件原声 + 平台音乐叠加，**这一条在 FB 端就是字面意义的"双音乐"**，与用户听到的冲突吻合；r1、r3 的 FB 版按记录为纯原声发布。
2. **queue/2026-10-22/v2.mp4 音轨装错**：build.sh 指定 Det6A4nIazf 音轨（atempo 0.96），实际文件里是 Dd9mefvBL7N 的音轨原样（s=1.00 未变速，频谱相关 0.998）。同目录的 **v2.bak.mp4 才是符合脚本的版本**。两份文件修改时间相同、体积仅差 339 字节、音轨却完全不同。**无法判定哪份是实际发布到 FB r2 的版本**——缺发布时的文件哈希/校验记录，本报告不猜。
3. **对照组结论（如实写明）**：有构建脚本的批次（2026-10-21 晚间三条、2026-10-22 的 v1/v3 与 v2.bak、2026-10-22-extra 四条、2026-10-23 三条 + p73057）**全部单轨干净**，脚本所述"先 -an 静音、再映射单一音乐轨"在声学上成立。
4. **系谱更正**：prep-2026-10-21.sh 对应的是已移入 queue/2026-10-21-recycled-bak 的那批，**不是**当前 queue/2026-10-21 的文件；当前三条是晚间批次，系谱在其 captions.md 中，声学结果与之一一吻合。另，posted.txt 中 10-21 三条的"（原声音频）"备注与文件实测不符（实测为已换轨的指定音乐），属记录错误。

## 方法论限制（不回避）

- DeQ2W0yCUAM / Dd9mefvBL7N / DeSM2jLhhw6 / DefE2l5hyH2 四条源音轨是**同一首歌**（包络互相关 0.98–1.00；DeSM 与 DefE 频谱互相关 0.985，为近同一实例）。凡源与乐同属此曲族的条目（fowler、2026-10-23/v2），包络与频谱都无法 100% 排除"同曲双份叠加"，结论只能是"无正证据 + 偏相关低"。但即使真叠，也是同一首歌，不构成用户所说的"两个音乐冲突"。
- queue/2026-10-22 的 v2 与 v2.bak 哪份被发布，文件层面无法判定（见点名 2）。
- 本次只审计文件本身；平台端在发布时叠加的音乐（如点名 1 的 r2）不在文件内，只能依据 posted.txt 记录指出。
